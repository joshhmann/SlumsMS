What reading the code showed

The plan was checked against release-1.6.4. These confirmed facts shaped the design:

Most of the action contract already existsLifeActivityQueue (one waiting and one active per bot, duplicate ends ignored), LifeAcceptance (admission), LifeExecutor (adapter), LifeOutcomes (how it ended). 1.7.0 grows these; it does not add a controller.
Bots get credit without proofEntering GRIND marks the current activity done (TrainingBot.java:575-579), so HELP_FRIEND "succeeds" on arrival and learning rewards it.
Engine faults shape personalityEvery failure, a logout included, lowers the bot's liking for that activity (LifeLearning.java:276-285).
Running activities have no deadlineOnly waiting requests expire (30 s). A path that never ends its activity can leave the bot busy forever.
Town EXP is wider than one activityMob level −1 is turned into 1 at 11 places in TrainingBot, so the fix goes where the training target is set.
Bot memory saves can't change versionLifeMemory wipes saves with an unknown version, and the 1.6.4 writer drops unknown keys. New data goes in as an extra key, and a round-trip test proves rollback is safe.

Action authority

LifeRuntime decides; the ledger owns execution truth. The existing executors keep all game mechanics. Every state change goes through one transition call, and nothing else can end an action.

Two actions conflict only when they claim the same resource, so chatting while grinding stays fine. Admission is all-or-nothing per bot, with no locks shared between bots. Parents claim only what they need throughout; each step claims its own.

Priority

safety › owner command › committed trade or PQ › the bot's own choice

Between two bots

  • Each trade, invite or help request has a transaction ID and a deadline on both sides.
  • A repeated or late answer is ignored.
  • A bot has only one pending request at a time, and the lower ID wins a simultaneous ask.
  • If the partner disappears, the action ends immediately.

Half-finished trades and purchases

  • Every transactional step writes a journal entry before it changes anything.
  • Cleanup never blocks the game loop: small slices per tick, database work off the tick, and a 2 s deadline spread across ticks. It reports done, pending or failed.
  • A bot keeps its claims while the outcome is uncertain.
  • Boot settles open entries before anyone logs in.

After a fix: each world-knowledge entry records what it depends on (capability, map, route, content version, switch). After a deploy or switch change, affected entries get a probe, at most one per capability per world every 10 min, so fixing the engine wakes bots back up.

Capabilities

A capability is something the engine or content must do for an action to be possible, such as quest.objective.credit or nav.portal.edge. States: missing broken unverified verified switched off

  • Bound to context. A verdict holds only for its server build, environment (simulation, TEST or live), content version, relevant switches and client build. If any of these differ, it reads as unverified.
  • Verified is not available. Whether the NPC is spawned or the route is open is checked at every admission. A short outage never downgrades a verdict.
  • Per character, every time. Level, job, items and permissions are checked fresh for each attempt.

The inventory covers navigation, map loading, NPCs, quests, combat, economy, persistence, social, scripting, WZ references and client protocol. Every failure gets a class: ENGINE CONTENT BOT CLIENT_PROTOCOL TEST_INFRA CONFIG_DEPENDENT.

Bot metrics

Each metric has its own denominator, so cancelling or rejecting actions can never make the numbers look better. Windows are rolling 1 h and 24 h; an eligible bot is online for at least half the window.

MetricOut of
Admission rateproposed actions

Ended within deadline (G2 target 99.9%)started actions
Cancellation and timeout ratesstarted actions
Repeated-failure rateeligible bots
Time to first meaningful progressp50 and p95 after login
AMPR, meaningful progress rateeligible bots

Counts as meaningful progress:

  • levels, job advances and real EXP gains;
  • quest steps;
  • new maps and arrivals at a planned destination;
  • net-worth gains and gear upgrades;
  • new bonds, parties that stick, PQ clears, accepted gifts and invites;
  • goal steps.

Doesn't count: chat, emotes, idle wander, breaks and repeated moves. AMPR gets thresholds after a week of baseline data and is not a 1.7.0 gate.
