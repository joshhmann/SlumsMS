## MIGRATIONS

Add both, in this order, using the file stems (no `.sql`), exactly as they appear in `database/migrations/`:

```
MIGRATIONS=(... 062-bot-relationship-axes 063-bot-memory-social)
```

- `062-bot-relationship-axes` — ten columns each on `botbond` and `botaffinity` (Familiarity, Trust, Affection,
  Respect, Attraction, Rivalry, Resentment, Obligation, Stage, HasAxes), all with defaults. Ledger id
  `062-bot-relationship-axes`. Rollback: `062-bot-relationship-axes.rollback.sql`.
- `063-bot-memory-social` — six columns on `botmemory` (SubjectType, Location, Confidence, Valence, Provenance,
  OtherParticipant), all with defaults. Ledger id `063-bot-memory-social`. Rollback:
  `063-bot-memory-social.rollback.sql`. It also relies on 030's Kind/Weight columns, which live already has.

Both are additive: an older jar runs fine on a migrated database, and the new jar runs without them but loses the
axes on restart and keeps the new memory fields in RAM only. Apply them before the new jar starts, and re-check
that `git diff --name-only v1.6.3 HEAD -- database/migrations` lists nothing else when the conf is finalised.

## UNIT_EDITS

None. Every social switch is a `-D` system property whose default is ON, so a build that ships these classes runs
the feature without any unit edit. The OFF line for each, if the owner wants a stage switched off at release:

```
-Dslums.modeswitch=false        mode switch (bots stay training bots; minds and bonds keep working)
-Dslums.socialacts=false        social acts between bots (no greet, chat, gift, argue, avoid)
-Dslums.socialbudget=false      per-pair cooldowns, turn limit and rate caps
-Dslums.intents=false           intents that outlive a tick ("meet me at 8")
-Dslums.botgifts=false          bot-to-bot gifts
-Dslums.sociallod=false         cheap social tick on far maps
-Dslums.bonds.background=false  background bond writes on busy maps
```

The mode switch additionally needs the daily-life brain: `-Dslums.botlife.enabled=true` and
`-Dslums.botlife.execute=true`, which live already has since 1.6.0.

## Checks

Auto-QA (lane-only, registered in `AutoQaCatalog`, documented in `docs/ops/qa-suite.md`): `t-ms-1`, `t-sm-1`,
`t-sa-1`. None is on the release allow-list, so none may SKIP in a release run; each SKIPs only when its flag is off
or the population is too small for the numbers to mean anything, and the SKIP line says which.

The Henesys pilot check (`t-pi-1`, probe `socialPilot`) is written and unit-tested but deliberately **not** in the
catalogue yet: until `SocialPilot` exists it could only SKIP, and a release run FAILs on an unexpected SKIP. Stage 8
registers it in the commit that lands the pilot (`Probes164SocialTest` fails if the class lands without it). It is
`t-pi-1` because `t-sp-1` is already the 1.6.2 "bots spread out" check.
