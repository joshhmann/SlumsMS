# 1.5.0: friendship and couple rings in the Cash Shop

Branch `gameplay-partner-rings-150` (from `test-1.5.0-rc3`).

## Why they were missing

Not the 1.4.0 pet-equip fix (that hid 355 newer pet equips, nothing else). The catalogue tool left them out on
purpose: `tools/cashshop/catalog_rules.py` `ring_record_needed` drops every ring with an `Effect.wz/ItemEff` look,
because such a ring only works when both players hold a copy tied to a `rings` row naming the other, and the window
had no way to make those rows. The generated header listed them as "ring needs a partner ring record (no partner
flow in the window)". Cosmic's own flow (`CashOperationHandler` 0x1D / 0x23) cannot help: it runs only inside the
stock Cash Shop stage, which the window replaces, and it sends the partner's ring as a locker gift nobody can open.

## What players see

Cash Shop, Ring category: 7 couple rings (1112001-1112003, 1112005-1112007, 1112012) and 6 friendship rings
(1112800-1112802, 1112810-1112812), at their stock v83 prices (3600-6000 NX; the price buys the pair).

1. Select one and press **Buy**. A Maple Administrator prompt asks for the partner's character name.
2. The partner must be another player online in the world (any channel). Bots, yourself, unknown and offline
   names are refused with a popup; nothing is charged.
3. Both rings are written to `rings` in one transaction, each player gets their copy straight into the Equip
   inventory (the partner with a popup), then the NX is taken. Any failure undoes everything.
4. Equip, change channel once (so each client loads its own ring record), stand near each other: the effect shows.

No gender check: two characters of the same gender can share a couple ring (owner decision). Buy Cart refuses
partner rings. Closing the prompt cancels. The same ring with the same partner twice is refused.

## Server changes

- `server/cashshop/CashShopPartnerRings.java` (new): the flow above. `scripts/npc/cashshop_partner_ring.js` is
  the prompt. `NPCScriptManager.dispose` tells it when the prompt closes.
- `CashShopWindowHandler.buy` routes partner rings to it; `CashShopWindowPurchase` refuses them in a cart.
- `CashShopWindowPackets.BUY_PARTNER_REFUSED = 9` (current DLL shows "Purchase failed." plus the server popup).
- `PacketCreator.addRingLook`: wrote every equipped ring after one flag byte; the client reads one record per list,
  so two equipped friendship rings broke the spawn/look packet. Now writes the first one only.
- `CashOperationHandler`: the commented-out gender check is replaced by a neutral note (no behaviour change).
- `!qa` `pr-1` / `pr-2` (docs/ops/qa-suite.md), QaLog topic `RING`.

## Catalogue

`catalog_rules.py` reads the ring ids from `CashShopPartnerRings.java` and sells those; every other ItemEff ring
(wedding/engagement, the post-v83 effect rings) stays out. `overrides.yaml` pins the ring band (type 111) at
4400, its pre-1.5.0 median, so no other ring's price moves. Diff: +13 rows, nothing else. Built and linted against
the bake WZ with `tools/colorprism/install_wz.py` applied (a scratch copy), as the Coloring Prism row needs.

## Live step (not applied)

The catalogue file and the server jar must go live **together**: an old jar would sell these rings as plain items
through the cart path (no ring records, no effect, no partner copy).

1. Deploy the 1.5.0 server build that contains this branch, plus `scripts/npc/cashshop_partner_ring.js`.
2. Copy `cashshop/catalog.tsv` from this branch over the live one (the server's working dir `cashshop/`).
3. Restart, or `!reloadcashshop` (GM 3) if the jar was already running. Open windows see the rows after reopening.
4. No database migration: the `rings` table already exists (Cosmic schema).

Rollback: put the old `catalog.tsv` back and `!reloadcashshop`. Rings already bought keep working.
