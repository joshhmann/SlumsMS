# 1.6.0: deploy steps outside the jar

Steps the 1.6.0 release needs that `docs/release/1.6.0.conf` and the generated `deploy.sh` do not do by themselves.
Whoever stages 1.6.0: carry each item into the deploy, the release notes and the QA checklist. Add new items below.

## 1. Custom NPC scripts on (`USE_ENABLE_CUSTOM_NPC_SCRIPT: true`)

What: owner decision 2026-10-26 (`docs/design/custom-npc-review.md`, "Decisions"). Branch `160-customnpc` makes the
custom NPCs safe to open; this config line turns them on:

| NPC | With the flag on |
|---|---|
| Coco 9000017 | Chaos Scroll 60% synthesis, at most 5 per talk (was 100) |
| Agent E 9000036 | accessory crafter; the "Belts" roll gives a belt 1132005-1132016 only (no medals); stat rings cost 1,000,000-2,000,000 mesos plus their materials |
| Dalair 9000040 | equipment merge: level 160 (110 Cygnus) and Maker level 3 always (USE_STARTER_MERGE no longer matters), at most 3 merges into any one item, a list of the items that will be destroyed and a yes/no before it runs, locked items never merged |
| Maple TV (mapleTV.js -> scroll_generator) | scroll generator, at most 5 prizes per character per day (quest record 32010, survives restarts) |
| Spiegelmann 2042000-2 | ore refining (menu option 4), unchanged |
| Asia 2082014, T-1337 9201101 | not affected any more: always the stock talk |

How: no longer by hand. `set-release-config` handles booleans since 1.6.0, so `docs/release/1.6.0.conf` has
`USE_ENABLE_CUSTOM_NPC_SCRIPT=true` in `SERVER_SET`: the generated `deploy.sh` flips it with the jar while the server is
down (its pre-check dry-runs the edit first), and `rollback.sh` restores `config.yaml` from the backup, so a 1.5.x jar
never runs with it on (1.5.x jars have the uncapped merge, the 100-per-talk Coco and the medal roll). The server reads
`config.yaml` at boot only.

TEST (`/opt/mapleroot-dev/persistence-test/Server`): `tools/ops/deploy-test` does not touch the config, so flip it
once with a backup, then restart the test server:
```
cd /opt/mapleroot-dev/persistence-test/Server
cp -p config.yaml config.yaml.pre-160-customnpc
<release worktree>/tools/release/set-release-config config.yaml --set USE_ENABLE_CUSTOM_NPC_SCRIPT=true
```

No migration: the merge count lives in the item's flag (bits 0x400/0x800, never sent to the client) and the daily
scroll prize count in a quest record.

QA after the restart (real client):
- Coco: the number box stops at 5; making 1 takes 1,200,000 mesos and the materials.
- Agent E: "Belts" -> "Try it!" shows as a real option and gives a belt; a Lilin's Ring (lv10) asks 1,000,000 mesos.
- Dalair on a level 160 character with Maker 3: the list of items to be destroyed appears before the yes/no; "No"
  keeps everything; the 4th merge into the same worn item is refused ("3 times") and destroys nothing. On a character
  under 160 or without Maker 3 he refuses.
- Maple TV: the 6th prize in a day is refused; mesos and supplies are kept.
- Asia (Leafre ship) and T-1337 (NLC): the stock talk, no shop.

## 2. Staff dashboard on live (ticket 108)

What: owner decision 2026-10-26. The live server writes the staff dashboard's snapshots (bots, health, chat counts,
accounts) every 60 s, and the dashboard page is served on the LAN only, behind the TEST dashboard's password. Design
and the exporter review: `docs/tickets/108-live-visibility.md`. This step lives here, not in the site's `LAUNCH.md`,
because `LAUNCH.md` is on the site branch (`site-160-theme`).

How:
- The JVM flags ride in the deploy: `docs/release/1.6.0.conf` `UNIT_EDITS` adds `-Dsolomapling.dashboard=true
  -Dsolomapling.dashboard.dir=/srv/slums-dashboard/data -Dsolomapling.dashboard.periodSeconds=60`. The rollback
  restores the old unit, which turns the snapshots off again.
- The page and nginx site are a separate, owner-run step (owner's go; it reloads the shared nginx on 164). Any time
  on release night, before or after the deploy, from a SlumsMS checkout on 187 at the 1.6.0 tag:
  ```
  tools/ops/install-live-dashboard          # prints the plan and read-only checks; changes nothing
  tools/ops/install-live-dashboard --go     # installs the page, the site on 192.168.0.164:8096, nginx -t, reload
  ```
  It refuses if 8096 is taken or TEST's htpasswd file is missing, never reloads a config that fails `nginx -t`, and
  logs nginx's pid and config hash before and after to `/var/log/slums-dashboard-install.log` (the pid should stay
  the same: a reload, not a restart). Undo: `tools/ops/install-live-dashboard --remove` (keeps the page and data).
- Not on release night: the hourly map export (Map tab) and the ops/GM extras timer. Both are optional; the GM page
  reads the live DB and needs its own go.

QA after the deploy:
- About a minute after the server is up, the live log has `Dashboard snapshots every 60s to /srv/slums-dashboard/data`
  and `/srv/slums-dashboard/data/live.json` exists.
- From a LAN PC, `http://192.168.0.164:8096/` asks for a password; the TEST dashboard login opens it and it shows
  live's bots online, players and tick time. From outside the LAN it is unreachable.
- `exportMs` in `live.json` stays well under 100.

## 3. Ranking pictures on live (owner, 2026-10-27)

What: the website's rankings show each character's look (96x96, drawn by `soloMapling.site.avatar.AvatarExport` from the
game data). It is an offline job in its own JVM at idle priority that never talks to the game server: every 15 min it
draws pictures for characters on the leaderboards whose look changed. On TEST it has run since 2026-10-27 12:50 UTC.
Found missing from the release by the 2026-10-27 switch audit.

How (owner's go; it installs a systemd unit on 164), after the deploy is up and the site export has written
`data/site/leaderboards.json`, from a SlumsMS checkout on 187 at the 1.6.0 tag:
```
scp deploy/site/slumsms-site-avatars.{service,timer} root@192.168.0.164:/etc/systemd/system/
ssh root@192.168.0.164 'systemctl daemon-reload && systemctl enable --now slumsms-site-avatars.timer && systemctl start slumsms-site-avatars.service'
```
Check: `systemctl status slumsms-site-avatars.service` ends `status=0/SUCCESS`, and the server's
`data/site/avatars/index.json` lists the board's names; the next site build shows the pictures. Undo:
`systemctl disable --now slumsms-site-avatars.timer` (the pictures stay; the site shows blanks without them).
