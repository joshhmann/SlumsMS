1.6.3 is 1.6.2 plus the NX house desk, the trader bots at the desk, companion lanes, planned bot replies, fads back on
with the b267 lock fix, the bot database pool and population-cap work, and fixes. This file holds the steps the 1.6.3
release needs that `docs/release/1.6.3.conf` and the `deploy.sh` it generates do not do by themselves. Whoever stages
1.6.3: carry each item into the deploy, the run sheet (`/root/work/agent-runs/server/1.6.3-night-server-steps.md`, which
this follows), the release notes and the QA checklist. Add new items below.

Times: UTC with PST (PST = UTC-8). Every live step needs the owner's go for that exact step.

## 1. NX desk funding at launch (P4: owner, with go; before the desk opens)

What: the house desk is stocked with **50,000 NX and 500,000,000 mesos** (owner 2026-11-01 14:55 UTC for the NX,
17:38 UTC for the mesos). The desk trades through SlumsBank, **account 15** (`-Dslums.exchange.houseAccount=15`,
unchanged from 1.6.2). SlumsBank's desk starts empty (its own NX went to the regulars), and its 1,500 NX and 15,000,000
mesos sit with the three regular trader bots today, so the money comes back first and the rest is granted. Nothing is
minted: every figure below moves a real balance.

The three funding commands only work on **account 15** (`Exchange.fundDeskLive` / `unfundHouseLive` refuse any other
account with `NOT_HOUSE`), so they are typed in game as SlumsBank, not on an admin character.

Order:

1. As SlumsBank, with the exchange running (section 2, step 2 done): `!exchange unfund 1`, `!exchange unfund 2`,
   `!exchange unfund 3`. Each cancels that regular's orders and moves its whole HOUSE (NX and mesos) to SlumsBank's
   payout **at once** — 1,500 NX and 15,000,000 mesos in total. The regulars stand down now the desk trades (owner).
2. Log account 15 out completely, then the owner runs the grant for the remainder (money: the owner's statement, not an
   agent's):
   ```
   UPDATE accounts   SET nxCredit = nxCredit + 48500       WHERE id = 15;
   UPDATE characters SET mesos    = mesos    + 485000000   WHERE id = <SlumsBank's character id>;
   ```
   `SELECT id, name FROM characters WHERE accountid = 15;` first; confirm the id with the owner before the second
   statement. 1,500 + 48,500 = 50,000 NX and 15,000,000 + 485,000,000 = 500,000,000 mesos. NX is the account's
   `nxCredit` (Cash Shop cash 1), mesos are the character's column; both must be logged out or the server's live
   wallet will write over the edit.
3. Log SlumsBank back in on a channel and run `!exchange desk fund nx 50000`, then
   `!exchange desk fund meso 500000000`. Each takes the amount **out of SlumsBank's own wallet** into the desk's HOUSE
   bucket (`FUND` posting, ledgered); the commands refuse in the Cash Shop or while changing channel.
4. Check: `!exchange status` shows the desk line `NX desk: open, R <r> (<x> mesos per NX), buy <a> / sell <b>; desk
   50000 NX / 500000000 mesos; moved today 0.00%`; `/var/lib/slums-market/outbox/nx-desk.json` has `"open": true`,
   `"desk_nx": 50000`, `"selling": true` and the same `mid`; one small player buy and one small sell fill on the desk
   and appear in `!exchange fills` with no "regular" marker on either side; their ledger rows carry the desk's bucket
   (`exchange_escrow` kind HOUSE, owner -100).

Rollback: the desk's money is escrow, not a gift. Do **not** run `058-nx-desk.rollback.sql` while either desk bucket is
non-zero: empty it first with `!exchange desk unfund` (all of it comes back to SlumsBank's payout at once), then roll the
migration back. Never roll back 038/044 with escrow or payouts non-zero, as before.

## 2. Exchange on the night (N4)

What: 1.6.3 comes up with the exchange **halted** (`-Dslums.exchange.startHalted=true`, unchanged from 1.6.2) and the
desk on (`-Dslums.exchange.desk=true`). With the desk on, the NX order book is off: resuming clears it.

Order, after the boot check (N2) and the owner's login check (N3), as SlumsBank:

1. Read the boot log: `journalctl -u slumsms | grep "NX exchange audit:"` must show `desk start R=<n> buy=<a> sell=<b>`
   and **no** `HALT` line. A `HALT desk state unreadable (…)` line means migration 058 is missing or row id 1 of
   `exchange_desk` will not decode: fix that before trading (the exchange is halted by design in that case).
2. `!exchange resume`. With the desk on this also cancels and refunds every resting NX order and prints
   `NX book off (desk): N orders cancelled, M NX returned to their owners`. Offline players' refunds land on their next
   collect.
3. `!exchange cancel-nx` — the belt-and-braces run (idempotent: it finds none and reports `0 still open`). If the step-2
   line said `still open`, this is where it must reach 0.
4. Section 1: fund SlumsBank's desk.
5. `!exchange status` — first line `Exchange: running, … NX escrow 0 NX / 0 mesos`; then a player buy and sell.

Rollback: `!exchange halt` stops all trading at once, then, if the desk itself misbehaves, drop
`-Dslums.exchange.desk=true` from the unit and restart. With the switch off the exchange is 1.6.2's order book and
`exchange_desk` is not read, so the migration can stay; the desk line disappears and the site removes `nx-desk.json`
rather than serve a stale quote.

## 4. After the night: fads and caps are watches, not switches

- **Fads are ON in 1.6.3** (owner 2026-11-01 14:55 UTC: "Turn it on now with the fix and see"). The b267 review asked
  for a 72 h fads-ON soak with 288 clean thread-dump samples; TEST's soak started 2026-11-01 09:35 UTC and ends **Wed
  2026-11-04 09:35 UTC**, after this release, so it is a watch. If thread dumps show a thread blocked on the Fads
  monitor, or the health sweep reports blocked threads, put the stopgap back (`-Dsolomapling.fads=false` in the unit,
  restart; owner go) and report it.
- **The caps are config-only.** 3,000 / 3,500 (owner 2026-11-01 14:31 UTC, after b273) is safe only if b273's TEST
  proof at full population was green by go/no-go. If the gate line shows refusals, or "Connection is not available"
  shows up in normal play, the answer is fewer bots (`BOT_ROSTER_PEAK_ONLINE` / `BOT_POPULATION_PEAK` back toward
  1200 / 1600), not a bigger pool. Back up live's `config.yaml` before any cap change; a restart applies it.
- **The monitor ships from the repo.** After the release, copy `deploy/monitor/` to 164 as `/opt/slumsms-monitor/` and
  run `sudo /opt/slumsms-monitor/install.sh live --status --news`. This carries the stale-roster bot count (rows with a
  login and no logout after a SIGKILL once showed 2,446 online when 1,186 were) and the release news item. The
  installed `live.conf` and `live.env` are kept; verify with `sudo slumsms-monitor check live --dry-run`.
