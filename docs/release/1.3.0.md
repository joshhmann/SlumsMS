## 1. Database migrations for live

All four are additive and recorded in the ledger table `mapleroot_integration_migrations`. Applying one twice changes nothing.

Before you start:
1. Stop the game.
2. Take a fresh backup with table locks (InnoDB and MyISAM), as in `docs/live-handoff-20261019.md`.

Apply in this order:

| File | Ledger id | What it does | Rollback |
|---|---|---|---|
| `database/migrations/003-solomapling-bots.sql` | `003-solomapling-bots` | New tables `botstore` (AUTO_INCREMENT 100), `botroster` and `botmemory`. No existing row changes. | `003-…rollback.sql` drops the three tables **and deletes every item row whose characterid is 1000000000 or higher** (bot items). |
| `database/migrations/005-bot-real-stats.sql` | `005-bot-real-stats` | Adds nullable stat, AP/SP and build columns to `botstore`, and a new `botskills` table. | `005-…rollback.sql` |
| `database/migrations/006-bot-yield-caps.sql` | `006-bot-yield-caps` | New `botyield` table, so daily meso counts survive a restart. Without it, the server keeps the counts in memory only. | `006-…rollback.sql` |
| `database/migrations/007-bot-starter-stash.sql` | `007-bot-starter-stash` | Nullable `botstore.StockedAt` (ticket 09, `shops` branch). ## 4. Template character

Every bot is cloned from one character, which `-Dsolomapling.template-id` names. It is left out of the rankings by id (`RankingLoginTask`), so make it a character nobody plays. On the test clones (`/opt/mapleroot-dev/solomapling-test`, `persistence-test`):
- The template is a dedicated **banned** account, `SMBotBase`, with a **non-GM** character `SMTemplate`, id 5 in the cloned DB.
- Sources: `docs/TASKS.md` MR-009, `docs/PROJECT-STATUS.md`, and `status.json` (`"template_id": 5`).

**No script or SQL in the repos creates the template.** It was made by hand in the clone. On live:
1. Register a new account, `SMBotBase`, through the normal flow.
2. Create one level-1 non-GM character on it in world 0, named `SMTemplate`.
3. Log out.
4. Set `accounts.banned = 1` for that account, so nobody can play it. Leave `gm = 0` on both the account and the character.
5. Read the character's id: `SELECT id FROM characters WHERE name='SMTemplate'`. Put it in `-Dsolomapling.template-id`.

The template's looks and stats do not matter, because bots are decorated or restored from `botstore`. Checked 2026-10-20: the test template is account `SMBotBase` (id 3, banned=1, never logged in) with character `SMTemplate` (id 5): world 0, level 1, Beginner (job 0), gm 0, map 993910000 (the Arcane hub where new characters start), 0 mesos, no inventory items. Make the live one the same way.

## 5. Nav cache (graph v68)

Live has no `cache/` directory at all. Without one, the first boot builds every graph on the two warm-up threads. v68 graph builds are 2 to 4.4 times slower than v61 (ticket 01), so expect a long warm-up with bots stalling on unbuilt maps.

1. **Pre-bake the graph cache.** Copy `cache/bot-nav/v68/` from the persistence test install into the live `Server/cache/bot-nav/v68/`, with the service stopped:
   - Path: `/opt/mapleroot-dev/persistence-test/Server/cache/bot-nav/v68/`
   - Size: 124 MB, 4,727 keys, the profiles bots actually used in the soaks.
   - **Unknown:** the copy is only valid if the test install's WZ matches live's server `wz/`. The `.bin` files carry the graph version, not a WZ hash, so this must be checked by the person deploying.
   - Alternative: re-bake on a staging copy of live's WZ:
     ```
     java -cp Cosmic.jar:test-classes -Dwz-path=wz -Dbot.nav.cacheDir=cache/bot-nav -Dbake.threads=4 soloMapling.ArtificialPlayer.GCMoveSystem.NavGraphBake <old v68 dir>
     ```
     `NavGraphBake` is in the test sources, so it needs a test-classes build.
2. **Deep bake.** The overlays live in `cache/bot-nav/deep/v68/<generation>/` with a `current` symlink. Run once by hand to seed it:
   ```
   java -Dbot.nav.cacheDir=cache/bot-nav -Dwz-path=wz -cp target/Cosmic.jar soloMapling.ArtificialPlayer.GCMoveSystem.NavDeepBake --all-maps
   ```
   - The 164 test run used a 20-minute budget and made 5.2 MB of overlays. The full set is 11,352 maps; the unit's budget is 150 minutes per night and the bake is incremental.
   - It also builds and saves any missing base graphs.
   - A running server picks up a new generation within a minute.
3. **Learned data.** `cache/bot-nav/learned` and `heat` start empty on live. Old-version learned files are migrated forward automatically (ticket 04).
4. **Disk.** The live root filesystem is 86% full, with 48 GB free. The cache is a few hundred MB; old deep generations are pruned to 3.

## 8. Rollback

**Bots off, keep 1.3.0.**
1. Set `-Dsolomapling.enabled=false -Dsolomapling.autopopulate=false` in the unit.
2. Run `daemon-reload` and restart.

Bot tables and rows stay in place and do nothing. The new `config.yaml` keys are fine with this jar.

**Back to 1.2.1.**
1. Stop the service.
2. If players have progressed since the deploy, take a backup.
3. Restore the 1.2.1 `target/Cosmic.jar` and the saved unit file (`-Xmx2G`, bots false).
4. **Remove every `BOT_*` key added to `config.yaml`, or restore the saved config.** The 1.2.1 jar does not know them, and an unknown key stops the boot.
5. Start and smoke test.

The migrations can stay: 003, 005, 006 and 007 only add tables and columns that 1.2.1 never reads. Bot item rows (characterid 1000000000 or higher) are ignored because no `characters` row matches. The client needs no rollback unless a 1.3.0 client was published with this release.

**Full DB rollback, only if needed.**
1. Apply `006-…rollback.sql`, then `005-…rollback.sql`, then `003-…rollback.sql`. The 003 rollback deletes every bot and all of their items.
2. Or restore the pre-deploy dump. That loses all player progress since the deploy.

**Nav caches.** Delete `cache/` to rebuild. Roll back a bad deep generation with `NavDeepBake --rollback`. Neither touches the DB.
