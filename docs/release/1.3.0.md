## 4. Template character

Every bot is cloned from one character, which `-Dsolomapling.template-id` names. It is left out of the rankings by id (`RankingLoginTask`), so make it a character nobody plays. On the test clones (`/opt/mapleroot-dev/solomapling-test`, `persistence-test`):
- The template is a dedicated **banned** account, `SMBotBase`, with a **non-GM** character `SMTemplate`, id 5 in the cloned DB.
- Sources: `docs/TASKS.md` MR-009, `docs/PROJECT-STATUS.md`, and `status.json` (`"template_id": 5`).

The test template was made by hand in the clone; the repos hold no script for it. The test template is account `SMBotBase` (id 3, banned=1, never logged in) with character `SMTemplate` (id 5): world 0, level 1, Beginner (job 0), gm 0, map 993910000, 0 mesos, and no inventory items, skills or keymap. The template's looks and stats do not matter, because bots are decorated or restored from `botstore`.

On live, create the same shape with the service stopped. This SQL was rehearsed on a copy of live on 2026-10-20 and gives a row identical to the test template apart from ids, date and rank. It takes well under a second. The password is not a valid hash, so the account can never log in:

```sql
START TRANSACTION;
INSERT INTO accounts (name, password, banned, banreason, tos)
  SELECT 'SMBotBase', '!bot-template-no-login', 1, 'SlumsMS bot template', 0
  WHERE NOT EXISTS (SELECT 1 FROM accounts WHERE name = 'SMBotBase');
INSERT INTO characters (accountid, world, name, level, job, gm, map, meso, gender, skincolor, hair, face)
  SELECT a.id, 0, 'SMTemplate', 1, 0, 0, 993910000, 0, 0, 0, 30000, 20000 FROM accounts a
  WHERE a.name = 'SMBotBase' AND NOT EXISTS (SELECT 1 FROM characters WHERE name = 'SMTemplate');
COMMIT;
SELECT c.id AS template_id, a.id AS account_id, a.banned, c.gm FROM characters c
  JOIN accounts a ON a.id = c.accountid WHERE c.name = 'SMTemplate';
```

Put `template_id` in `-Dsolomapling.template-id`. It was 6 on the rehearsal copy, but read it; don't assume it. The hand-made route also works: register `SMBotBase` in the normal flow, create a level-1 character `SMTemplate` in world 0, log out, and set `accounts.banned = 1`. Keep `characters.gm = 0`; `accounts` has no `gm` column, and `webadmin` stays 0. A client-made character carries starter items and a keymap, which the SQL route avoids.

## 5. Nav cache (graph v68)

Live has no `cache/` directory at all. Without one, the first boot builds every graph on the two warm-up threads. v68 graph builds are 2 to 4.4 times slower than v61 (ticket 01), so expect a long warm-up with bots stalling on unbuilt maps.

1. **Pre-bake the graph cache.** Copy `cache/bot-nav/v68/` from the persistence test install into the live `Server/cache/bot-nav/v68/`, with the service stopped:
   - Path: `/opt/mapleroot-dev/persistence-test/Server/cache/bot-nav/v68/`
   - Size: about 131 MB on disk (276 MB apparent), 4,986 files on 2026-10-20. It keeps growing while the test server runs. These are the profiles bots actually used in the soaks.
   - The copy is only valid if the test install's WZ matches live's server `wz/`. The `.bin` files carry the graph version, not a WZ hash, so recheck this right before copying. On 2026-10-20 the whole `wz/` tree was identical (sha256 over every file, sorted): `Map.wz` `ead4c6489d9538eb`, all of `wz/` `365335ea1d520369` on both installs. Command, run from inside each `wz/`: `find Map.wz -type f -print0 | sort -z | xargs -0 sha256sum | sha256sum`.
   - Alternative: re-bake on a staging copy of live's WZ:
     ```
     java -cp Cosmic.jar:test-classes -Dwz-path=wz -Dbot.nav.cacheDir=cache/bot-nav -Dbake.threads=4 soloMapling.ArtificialPlayer.GCMoveSystem.NavGraphBake <old v68 dir>
     ```
     `NavGraphBake` is in the test sources, so it needs a test-classes build.
2. **Deep bake.** The overlays live in `cache/bot-nav/deep/v68/<generation>/` with a `current` symlink. Run once by hand to seed it:
   ```
   java -Dbot.nav.cacheDir=cache/bot-nav -Dwz-path=wz -cp target/Cosmic.jar soloMapling.ArtificialPlayer.GCMoveSystem.NavDeepBake --all-maps
   ```
   - The 164 test run used a 20-minute budget and made 5.2 MB of overlays. The full set is 11,352 maps; the unit's budget is 150 minutes per night and the bake is incremental.
   - It also builds and saves any missing base graphs.
   - A running server picks up a new generation within a minute.
3. **Learned data.** `cache/bot-nav/learned` and `heat` start empty on live. Old-version learned files are migrated forward automatically (ticket 04).
4. **Disk.** The owner grew the root filesystem on 2026-10-20: 430 GB, 147 GB free (66%). The cache is a few hundred MB; old deep generations are pruned to 3.

## 8. Rollback

**Bots off, keep 1.3.0.**
1. Set `-Dsolomapling.enabled=false -Dsolomapling.autopopulate=false` in the unit.
2. Run `daemon-reload` and restart.

Bot tables and rows stay in place and do nothing. The new `config.yaml` keys are fine with this jar.

**Back to 1.2.1.**
1. Stop the service.
2. If players have progressed since the deploy, take a backup.
3. Restore the 1.2.1 `target/Cosmic.jar` and the saved unit file (`-Xmx2G`, bots false).
4. **Remove every `BOT_*` key added to `config.yaml`, or restore the saved config.** The 1.2.1 jar does not know them, and an unknown key stops the boot.
5. Start and smoke test.

The migrations can stay: 003, 005, 006 and 007 only add tables and columns that 1.2.1 never reads. Bot item rows (characterid 1000000000 or higher) are ignored because no `characters` row matches. The client needs no rollback unless a 1.3.0 client was published with this release.

Restore the 1.2.1 `src/main/java/soloMapling` files from the backup too. 1.2.1 with bots off reads none of them, but a later bots-on test of the old jar would.

Rehearsed 2026-10-20: bots-off 1.3.0, the 1.3.0 jar with the unchanged live `config.yaml` and the 1.2.1 flags, and the 1.2.1 jar with the migrations kept all booted with 0 errors.

**Full DB rollback, only if needed.**
1. Apply `007-…rollback.sql`, then `006-…rollback.sql`, then `005-…rollback.sql`, then `003-…rollback.sql`. The 003 rollback deletes every bot and all of their items. The template account and character are not removed; delete them by hand if wanted.
   - Rehearsed 2026-10-20: 0.7 s. The ledger went back to 001 and 002. 0 bot items were left. `CHECKSUM TABLE` on `inventoryitems`, `inventoryequipment`, `skills` and `queststatus` matched the pre-upgrade copy. 1.2.1 booted with 0 errors.
