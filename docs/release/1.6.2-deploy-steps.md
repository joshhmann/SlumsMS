# 1.6.2: deploy steps outside the jar

1.6.2 ships everything built for 1.6.1 (there was no separate 1.6.1 release) plus alts, the exchange, Maker and ports.
Steps the 1.6.2 release needs that `docs/release/1.6.2.conf` and the generated `deploy.sh` do not do by themselves.
Whoever stages 1.6.2: carry each item into the deploy, the release notes and the QA checklist. Add new items below.

## 1. Slums-chan (NPC 9990000) in the server's WZ (owner-run on release night)

What: Slums-chan replaces Cody in the first-login welcome window and `@settings`, and stands in Base of Roots and
Henesys (migration `042-slums-chan-npc`, listed in `1.6.2.conf`). The server reads NPC names from the host WZ, which is
not in git, so her name has to be added there: an `Npc.wz/9990000.img.xml` file and an entry in `String.wz/Npc.img.xml`
(`name "Slums-chan"`, `func "SlumsMS Guide"`). Without it the server still runs, but her name tag reads MISSINGNO.
The 1.6.2 client brings her picture and name on its own (`Data/Npc/9990000.img`, `Data/String/Npc.img`, both in
`tools/release/client-allow.txt`).

How, with the game stopped, from a checkout at the 1.6.2 tag (the tool backs up `String.wz/Npc.img.xml` to
`<server>/wz-backup-<UTC stamp>-slums-chan-<pid>/` first, a new folder each run, and does nothing on a second run):
```
cd "/opt/mapleroot/MapleRoot Full Repack/Server"
python3 <checkout>/tools/data-align/add_slums_chan.py --wz wz             # dry run: prints the two edits
python3 <checkout>/tools/data-align/add_slums_chan.py --wz wz --apply
```
Order: stop, database backup, this step, the jar, migration 042, start (the WZ is read at boot).

Rollback: copy `wz-backup-<stamp>-slums-chan-<pid>/String.wz/Npc.img.xml` back over `wz/String.wz/Npc.img.xml`, delete
`wz/Npc.wz/9990000.img.xml`, run `database/migrations/042-slums-chan-npc.rollback.sql`.

TEST: applied 2026-10-28 to `/opt/mapleroot-dev/persistence-test/Server/wz` (backup `../wz-backup-<stamp>`).

QA (real 1.6.2 client): a new character on Base of Roots sees her near the spawn point; she stands in Henesys on the open street left of the stall (x 1040, migration 048, needs a restart);
 a click shows her welcome with "Show me around" (the guide) and "My settings"; the first-login guide
window shows her face and name. (An older client without her files does not just show no picture: see the correction below.)

**Correction (TEST 2026-10-28 09:16-09:24 UTC):** an older client does break. A client without `Npc/9990000.img` that
is sent her SPAWN_NPC hits STG_E_FILENOTFOUND and CWvsApp::Run ends: an orderly disconnect about 1.5 s after entering
Henesys or Base of Roots (AqClient on the 1.6.0.2 client, build 10601). Branch `161-dcfix` gates custom NPCs per
session (`server.life.CustomNpcGate`; config `CUSTOM_NPC_IDS` = `9990000,2985-2999` and `CUSTOM_NPC_MIN_BUILD` = 10610 are code defaults, not set in `1.6.2.conf`):
their spawn/controller packets are not sent to a client without the data, and a talk window they frame is framed by
Cody instead. Who has the data: a build stamp format 2 (1.6.2-rc5 = 10650 and later) with caps bit 0; a format 1 stamp,
or none, falls back to build >= 10610. The login session's stamp is now carried to the channel session
(`ClientStampCarry`); before this the channel always read build 0 (so the 1.6.0.2 Edit UI login tip never showed;
it will now, once, for a 10600+ client).
**Live MIN_CLIENT_BUILD for 1.6.2 must still be at least the final 1.6.2 client build;** this gate is the second net.
QA: on the old 1.6.0.2 client, enter Henesys and Base of Roots: no Slums-chan, no disconnect; `@settings` opens framed
by Cody. On the 1.6.2 client: she stands in both maps and frames the windows.

## 4. Release-night order (written at staging, 2026-10-28)

`tools/release/release` runs stop-backup -> publish-client -> apply-start -> smoke -> maintenance end in one go and has
no slot for the WZ steps (only `release-live.sh` runs `extra/extra-steps.sh`, and that one publishes no client). So run
sections 1, 2 and 3 **just before** `tools/release/release`, while 1.6.0.2 is still up. That is safe: the server reads
`String.wz/Npc.img.xml` once, at class load (`LifeFactory`), so the running 1.6.0.2 never sees the new names (only GM
`!search npc` re-reads it), and it has no plife rows for 9990000/2985-2999. The 1.6.2 start after the jar picks them up.
If the release rolls back, the extra names are harmless; restore the String file only if you want it exact.

**Backup gap (fixed 2026-10-28, kept as belt-and-braces):** before the fix both tools backed up
`String.wz/Npc.img.xml` to `wz-backup-<UTC second>/`, so run back to back within the same second the penguin run
overwrote Slums-chan's backup with the already-edited file (seen on a scratch copy of live's file). Each tool now
writes to its own new folder, `wz-backup-<UTC stamp to the microsecond>-<tool>-<pid>/` (`slums-chan` or
`lazy-penguins`), and stops without writing anything if that folder or file already exists. The own copy and the
`sleep 2` below are therefore **no longer required**; they cost nothing, so keep them as a second net. The pristine
file is the backup in the `-slums-chan-` folder (or your own copy):
```
cd "/opt/mapleroot/MapleRoot Full Repack/Server"
cp -p wz/String.wz/Npc.img.xml wz-backup-pre-1.6.2-Npc.img.xml     # sha256 720fd566309e... on 2026-10-28
python3 <checkout>/tools/data-align/add_slums_chan.py --wz wz --apply
sleep 2                                                              # optional since the fix
python3 <checkout>/tools/data-align/add_lazy_penguins.py --wz wz --apply
python3 <checkout>/tools/data-align/add_slums_chan.py --wz wz; python3 <checkout>/tools/data-align/add_lazy_penguins.py --wz wz   # both: nothing to do
```
Checked on a scratch copy of live's `String.wz/Npc.img.xml` (2026-10-28): 16 NPC files added, the XML parses, a second
run does nothing.

Then the release (client = 1.6.2-rc2, build 10720 from the fixed VERSION formula, no override flags (owner 2026-10-30,
b205); staged with `stage-client`; `MIN_CLIENT_BUILD=10720` in
`1.6.2.conf`). The client must not go out while 1.6.0.2 runs (it does not read stamp format 2); `release` publishes it
only while the server is down and restores the old manifest before any restart of the old version.


## Nav cache v70 and the dashboard extras (Server Dev, 2026-10-31)

**Prebuilt v70 nav cache (b109 bumps the nav graph to v70).** Without it, live's first boot rebuilds every map's graphs on
the two warm-up threads and bots stall on unbuilt maps. Server Dev bakes it on 187 before the night, from TEST's v69 key
list (14,611 keys on 2026-10-31) against a copy of TEST's WZ, with the 1.6.2 release jar:
```
# on 187, after the 1.6.2 jar and test-classes are built in /root/work/SlumsMS-162-release
B=/root/slums-nav-v70; mkdir -p $B/cache/bot-nav $B/keys
rsync -a root@192.168.0.164:/opt/mapleroot-dev/persistence-test/Server/wz/ $B/wz/
rsync -a root@192.168.0.164:/opt/mapleroot-dev/persistence-test/Server/cache/bot-nav/v69/ $B/keys/v69/
cd /root/work/SlumsMS-162-release && java -cp target/Cosmic.jar:target/test-classes -Dwz-path=$B/wz \
    -Dbot.nav.cacheDir=$B/cache/bot-nav -Dbake.threads=4 soloMapling.ArtificialPlayer.GCMoveSystem.NavGraphBake $B/keys/v69
rsync -a $B/cache/bot-nav/v70 root@192.168.0.164:/root/slums-nav-v70-live/      # staging copy on 164, not live's tree
```
Then `NAV_CACHE_SRC="/root/slums-nav-v70-live/v70"` in 1.6.2.conf before `gen-deploy`; `apply-start` copies it into
live's `Server/cache/bot-nav/` while the server is down (deploy.body.sh). The cache is only valid if live's Map.wz equals
the WZ it was baked on. On the night, before staging, the owner runs inside live's `Server/wz`:
`find Map.wz -type f -print0 | LC_ALL=C sort -z | xargs -0 sha256sum | sha256sum | cut -c1-16`
and it must print `df767cfeb52a2f40` (TEST's Map.wz on 2026-10-31; the `LC_ALL=C` matters: another sort locale
gives a different hash for identical files). If it differs, leave `NAV_CACHE_SRC=""`: the boot
still works, it just warms up slowly.

**slums-dashboard-extras (b109's dead-end/pit columns).** One binary on 164, `/usr/local/bin/slums-dashboard-extras`,
