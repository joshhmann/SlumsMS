# 171: Make 1.6.3 stabilization QA incremental, scripted and formally triaged

Owner-agreed direction, recorded 2026-10-31 (UTC and PT). Target: **1.6.3 stabilization and balancing**.
This records the decisions reached with the owner; implementation has not started. Current execution status
belongs in the release book and exported STATUS file. Do not add this work to 1.6.2's release requirements.

Coordinator owns scope and triage with the submitter; Server Dev owns server checks and integration;
Client Development owns scripted client execution/capture. Lane owners assign fixes only after ticket acceptance.

## Why

The owner expected functional altbots but saw entities that only spawned/floated, encountered broken maps, and
watched 1.6.1/1.6.2 expand as testing uncovered defects and suggestions. Long full-suite waits delayed feedback,
while visual behavior and whether a feature actually worked remained uncertain.

Priorities: faster feedback, finding more bugs, and actionable failure diagnosis. Longer unattended test windows
are acceptable. Manual review is acceptable, but client actions should be scripted to reduce operator error.
An existing QA environment is available; moving infrastructure is not a prerequisite.

## Owner decisions

- Do not ship a feature until its promised player behavior is functional; spawning or configuration alone is not
  acceptance. Missing proof remains unverified, not complete.
- Keep a required client pass, with repeatable scripts and recorded evidence.
- Check maps systematically, distinguishing structural checks from actual client traversal/rendering coverage.
- Focused checks unlock review/TEST integration; full regression and client acceptance gate the final release.
- Pause new feature starts in a lane while its verification backlog is unresolved; exceptions require a recorded
  scope decision. Continue work needed to obtain proof.
- Coordinator **and submitter** judge admission of newly discovered defects. Discovery does not authorize a fix.
- Every failure must be formally triaged and ticketed before fixing. An accepted existing ticket may be linked;
  do not create duplicate cards for the same defect.
- Balancing begins with version-specific vanilla/official numbers and explicitly justified SlumsMS adjustments,
  including economy effects. Do not change numbers merely because a test result looks surprising.

- **Live emergency path** (owner "yee", ~02:45 UTC 2026-11-01 / 7:45 PM PDT Oct 31). A live S1 mitigation that is
  configuration or flag only (for example the 1.6.2 night's bot caps `BOT_ROSTER_PEAK_ONLINE 1200 /
  BOT_POPULATION_PEAK 1600`, or `-Dsolomapling.fads=false`) may be applied on the owner's explicit go before triage.
  It is recorded afterwards as a card with the mitigation, the evidence and the rollback. Any code fix for the same
  defect still goes through triage and an accepted ticket.
- **Submitter for automated findings** (same approval). When a scripted or auto-QA check fails, the lane that owns the
  check is the submitter for triage, so the owner does not sign off on every failed check. The owner still decides
  anything that changes gameplay or the economy, and anything the owner reported themselves.
- **Existing cards count** (same approval). An existing card on the release book's board counts as the accepted
  ticket for S4 and other small fixes; no new ticket is needed. Those fixes keep the current lane rule: a
  fail-before/pass-after test, review, and the card's named CLOSER and PROOF.

## 1. Required failure-to-fix workflow

`check fails -> evidence captured -> coordinator + submitter triage -> ticket accepted -> fix assigned -> focused
recheck -> required client pass -> closure`

Diagnostic evidence gathering may continue before triage. Product changes, test/staging repairs and balance
adjustments wait for accepted ticket scope. This ticket establishes the process; it is not blanket approval to
fix every failure. New unrelated findings from an existing fix return to triage.

Day-to-day triage is run by the SlumsMS bug triage session on the Coordinator's behalf; admission and scope
disputes come to the Coordinator, and anything gameplay- or economy-changing to the owner.

Triage records:

1. Classification: product defect, test/staging defect, environment problem, or inconclusive evidence.
2. New ticket id or canonical existing ticket, with linked affected checks and reports.
3. Expected vs observed behavior, reproduction/preconditions and relevant evidence.
4. Severity/impact and disposition: admitted to 1.6.3, deferred with target/reason, duplicate, or needs investigation.
5. Coordinator/submitter decision, accountable fix owner and verifier.
6. Bounded acceptance criteria, focused rechecks and any required client evidence.

Inconclusive results need an investigation ticket before corrective work, not a guessed gameplay patch. Existing
tests remain failed/blocked/inconclusive until their evidence supports a verdict. Independent checks may continue;
checks whose prerequisites failed remain blocked rather than producing misleading downstream failures.

## 2. Acceptance contracts and incremental checks

Before implementing a stabilization fix, define starting state, player actions, expected outcome, automated check
ids and required client scenario. Track implementing, review, merged, deployed to TEST, awaiting proof, accepted,
with an explicit blocked reason where needed. One canonical acceptance result may close linked duplicate cards.

Three feedback stages:

- **Focused development:** reproduction and affected tests, with useful failure state. Keep current required
  fail-before/pass-after and full-suite lane rules unless separately revised through an accepted process change.
- **Incremental TEST:** use affected scenarios/checks without waiting for the full catalog. Focused evidence can
  unlock review/integration after required local checks. Schedule broader shared-system checks at explicit
  checkpoints; a failed checkpoint gets an owner and stops further feature starts in that lane.
- **Frozen candidate:** full normal-clock release regression, required scripted client passes, existing deployment
  rehearsal and compatibility/configuration checks. Targeted, old/carried or fast-mode results do not replace the
  final gate. Preserve existing skip/waiver policy; do not turn missing visual evidence into PASS.

Report results per completed check, not only at the end of the full run. Long checks expose progress, last useful
event and bounded timeout/stall reasons. Do not shorten legitimate gameplay timing just to meet a feedback target.
Specific latency targets remain to be measured and agreed; no 5/15-minute guarantee was adopted.

## 3. Scripted client evidence and first pilot

Use the existing QA environment and ticket 166 runner/capture work. Start with **altbots across representative
maps**, based on the owner's reported failure, rather than adopting every upstream tool at once.

| Scenario step | Required outcome/evidence |
| --- | --- |
| Spawn and stand | Grounded server state and client capture showing correct placement |
| Follow across platforms | Defined checkpoints reached; movement trace and visible movement |
| Change map through portal | Correct destination and resumed following |
| Fight and loot | Damage/inventory outcome plus visible attacks, movement and collection |
| Owner death/separation | Explicit expected recovery behavior, server evidence and client capture |
| Dismiss/end | Correct disappearance and cleanup; no stranded party/instance resources |

Scripts set up disposable actors, wait on readiness signals, perform repeatable actions, capture synchronized
client/server evidence and clean up on success or failure. Use normal movement, combat and interaction paths;
do not teleport past a broken obstacle or force an outcome to make the test pass. Scripted staging shortcuts
must be labeled and cannot prove the gameplay action they bypass.

Ambiguous visuals are reviewed by a person. Missing frames/signals or failed capture are inconclusive. Server
execution/dispatch is not proof of correct rendering. Record script hash, run/check id, server commit, client
build/artifact identity, relevant data/configuration and timestamps.

## 4. Map coverage

Define the map inventory and report separate coverage levels:

- Structural validation over all available map data: relevant portals/destinations/scripts, references and geometry
  invariants that existing tooling can establish. Missing input data is explicit, not silently counted as checked.
- Scripted client traversal/rendering checks for critical routes, representative geometry and known broken maps.
  Record the selected maps and why; expand based on triaged defects.
- Gameplay acceptance on a route checks actual traversal and continued behavior, not just that the map loads.

A structural pass is not a client pass. Do not claim every map was visually verified from a sample. Prioritize
coverage of actual broken-map reports and the altbot pilot before creating a broad new map-testing framework.

## 5. Actionable failure report minimum

Every failure submission includes:

- Failed action/check and expected vs observed outcome.
- Actor/run, map/stage, target and relevant state/preconditions.
- First failed step, last progress event, elapsed time and known blocking condition; unknown stays unknown.
- Synchronized clip/screenshots where relevant, server/client traces and exact build/script/data identities.
- Reproduction and a proposed diagnostic next step, separated from suggestions for new behavior.
- Triage status and ticket link once assigned. Until acceptance, clearly state that a fix is not authorized.

Example: altbot reaches the source portal but remains for 30 seconds; expected destination entry and resumed
following; no portal interaction recorded; attach client clip and movement trace. Do not conclude the cause from
silence alone. The coordinator and submitter classify/admit the issue before code changes.

## 6. Balancing evidence

Each accepted balance ticket records the vanilla/official baseline version and source, existing SlumsMS override,
intended gameplay/economy effect, proposed adjustment and measurement/acceptance bounds. Distinguish defects in
implementation or measurement from deliberate balance choices. Validate casting rates, damage accounting and
dummy limitations before trusting DPS comparisons. Economy changes still require the owner's decision.

## 7. Reuse upstream QA patterns selectively

Follow [169](169-botstory-qa-reference-adoption.md) and [170](170-cosmic-agents-qa-reference-adoption.md) for pinned
sources, provenance, overlap and limits:

- BotStory execution probes and phase-specific diagnostics: identify where an action failed server-side.
- cosmic_agents controlled movement fixtures: reproduce traversal cases quickly with useful traces.
- Measurement validity and lifecycle checks: protect real invariants without pretending mocks prove live behavior.

Adapt to SlumsMS's existing runtime and tools. Do not import another Agent runtime, add a full world replay engine,
or make completion of every upstream candidate part of this process ticket.

- Coordinator publishes the 1.6.3 admission/triage workflow and acceptance owners using the existing tracker.
- The altbot pilot has repeatable focused tests and a scripted client journey with retained failure/success evidence.
- At least one real discovered failure passes through triage and accepted ticket scope before its fix, followed by
  focused recheck and the required client proof. Do not manufacture a bug to satisfy this requirement.
- Map structural/client coverage and gaps are explicitly reported; a bounded expansion plan has an owner.
- Incremental results arrive before full-run completion, and the final release gate remains intact.
- Broader improvements have separate dispositions; report what is implemented, unverified and deferred.

First action for Claude: reconcile with existing QA tooling and accepted tickets, then scope the smallest pilot
implementation. Do not begin fixing newly observed product, harness or environment failures before formal triage.
This ticket authorizes no live action or deployment and adds no requirement to the 1.6.2 closure list.
