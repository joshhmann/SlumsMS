# Handlers: Trade, Storage, Merchants

Scope: the player-to-player trade window, account storage, hired merchants plus Fredrick retrieval, Duey parcel delivery, and the small interaction handlers that ride the same packets (messenger, gift notes, name transfer, rings/weddings, spouse chat), plus the GM buyback transaction store.

## Purpose

These handlers move items and mesos between players and between a player and the database, so every one of them is a duplication and loss surface: a trade window, a storage trunk, a hired merchant and a Duey parcel each hold items outside any inventory, and each has to survive a crash, a disconnect or a hostile client. The subsystem also owns the persistent side effects that must be atomic with the character save — the `storages` row and the storage items are written inside the character-save transaction ([src/main/java/client/Character.java:10305-10315](src/main/java/client/Character.java:10305)), and cards b294 (silent storage data loss) and b267 (live lock hang on `PlayerStorage`) are the two incidents that shaped its current locking and error-propagation rules. Everything else here — merchant mesos parked in `characters.MerchantMesos`, Fredrick's offline storage, Duey's `dueypackages` rows — is a smaller variant of the same "value outlives the session" problem.

If it trusts the server's per-type lists, the `sendStorage` whole-list fill ([src/main/java/server/Storage.java:256-258](src/main/java/server/Storage.java:256)) would show every stored item under every tab; nothing in the repo proves which side filters, and no client-side test exists.
2. Which exact statement ordering made b294's `DELETE` commit while the reinsert did not? The commit message and `StorageSaveFailureRollbackTest` establish the asymmetry, but the audit never named the storage-database engine's behaviour on a failed statement inside an open transaction — that would need the external schema/DDL.
3. Where is the `storages` / `fredstorage` / `dueypackages` / `transactions` DDL? No `CREATE TABLE` exists in the repository, so the column defaults (`slots = 48`) and the `MerchantMesos` type can only be confirmed against the live database, which was out of scope.
4. Is the b267 lock-order rule guarded anywhere now? The fix landed with a `FadsLockOrderTest` on its branch, but no such test is present under `src/test/java`, so a future caller of `PlayerStorage` from inside a monitor would not be caught here.
5. What closes a merchant on channel shutdown versus world restart — `forceClose` is called from both the map teardown and the 24 h schedule, and the `forceClosed` latch makes whichever arrives second a no-op, but the ordering between the channel's `dispose()` and `World.runHiredMerchantSchedule` was not traced.
6. Does `useEnforceMerchantSave` really flush on every add in live, or only on close? The switch defaults to true and the call sits at [src/main/java/net/server/channel/handlers/PlayerInteractionHandler.java:666-671](src/main/java/net/server/channel/handlers/PlayerInteractionHandler.java:666), but the live conf sets no overrides, so the live behaviour is the default — unverified on a running server.
