## New findings requiring formal triage before fixing

### A1. Sibling-only upgrade offers cannot pass the command's eligibility gate

Source-confirmed; proposed S3. [Ticket 178](../../tickets/178-sibling-only-upgrade-handover.md).

Ticket 99 marks owner/sibling sharing done. `CompanionItems.upgrades` considers both kinds of recipient and
`offerLine` tells the owner to request a trade. But `firstWithSomething -> has(TRADE_UPGRADES)` checks only
`List.of(leader)`. A piece that improves only a sibling therefore never reaches the sibling-capable handover.

Anchors in `src/main/java/soloMapling/ArtificialPlayer/BotPartySystem/CompanionItems.java` at the reviewed commit:
dispatch 60, entry gate 71-96, offer 233-270, handover 312-344. `GearUpgrades.java:61-96` scores each recipient.
`qa/OwnedAltScenarios.java:55` describes a mixed owner+sibling scenario, which can conceal the sibling-only case.
No Java/client reproduction was run; acceptance requires a dispatch-level regression and targeted client evidence.

### A2. Batched readiness events are lost to later waits

Reproduced locally; proposed S4. [Ticket 179](../../tickets/179-qa-worker-loses-batched-ready-events.md).

Actual `SilviaWorker`, fake transport/clock: a batch has `worldselect.ready` and `channels.ready`. Wait 1 succeeds;
wait 2 times out although the latter event is retained in the run's `seen` evidence. `events` advances the entire
batch cursor (`qarunner.py:363-370`), while `wait_signal` reads only newly fetched events (`443-465`).
The checked-in audit reproducer preserves the failure without touching production code. All 73 existing runner
tests pass, showing that their coverage misses this sequence. A correct repair must also prevent stale signals
from satisfying a newly armed action; merely searching all history is not sufficient.

## Existing-ticket acceptance gaps, not duplicate gameplay bugs

### B1. Draft client scenarios exceed real worker capabilities (166 / 171)

Every one of the 15 `qa-scripts/*.yaml` files is marked draft. In the actual worker:

- `SIGNALS` supports only world/channel/character/field readiness (`qarunner.py:332`); `field.ready` payload
  filtering is refused, including map id. `botme-alt-basics.yaml` requires both map id and `chat.received`, which
  the worker cannot supply.
- `character` has build identity but no character id/name (`476-501`), limiting actor-scoped feed waits.
- `capture` explicitly refuses chat log, packet trace and sample collection (`504-507`).
- A second alias does not select a second client instance: `login` uses the same transport and stops a running
  client before starting its replacement (`384-397`); actions do not carry instance identity. Thus the two-client
  b233/ring scenarios cannot be treated as supported by alias names alone.

These are acknowledged partial implementation paths, not a claim that no screenshots or manual checks ever
happened. Keep 166/171 open for concrete capability milestones and attach real run folders before promotion.
The verdict tool correctly requires recorded review for visual items (`qaverdict.py:114-127`); retain that guard.

### B2. t-bq-1 proves component execution, not the promised autonomous journey (158 / s23)

`Probes162.botQuest:268-372` freezes the bot (`281`), injects the active quest, places it at start/hunt/end maps
and NPC positions, then directly calls `BotQuests.atNpc`. It does run real quest and damage paths, so it provides
valuable legal-progress proof. But broken life-plan selection, cross-map navigation or NPC approach could coexist
with a green result. Needed acceptance: normal planner chooses/takes the quest, traverses it and returns through
normal paths, with recorded client evidence; retain this component probe as a faster prerequisite.

### B3. t-jb-1 accepts fallback as success (159 / s24 / b266)

`Probes162.errandProblems:1509-1531` accepts `arrived == 0` if `fellBack > 0`, the errand ended and the job changed.
The scenario explicitly allows that outcome. This proves the fallback prevents a stuck character; it does not
prove the instructor was reached. Keep fallback and successful-arrival obligations separate. Existing b266 means
the current routing issue should be reconciled there, not duplicated as a new unimplemented feature.

### B4. Nightly map check has a much smaller guarantee than "maps work" (157 / 171)

`NavProbeScenarios.Nv1Probe.MAPS` is six towns. Unreachable spots are diagnostic leads, intentionally not failure
verdicts; `MAX_LINES_PER_MAP=20` also bounds displayed detail. `NavTrapQa` detects new traps relative to a known
baseline, rather than repairing all known traps. `MapRouting` covers curated bad destinations. All are useful but
none proves all maps are navigable/renderable. Under 171, publish the inventory, known exceptions, structural
coverage and scripted client routes separately, then triage newly reproduced failures before fixing.
